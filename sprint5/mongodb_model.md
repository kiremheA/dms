# Модель MongoDB

**Обязательное —** Зафиксировать, какие данные принадлежат PostgreSQL, какие будут принадлежать MongoDB и где находится источник истины.

В целевой модели PostgreSQL — источник истины для устройств, заявок и категорий; MongoDB хранит определения полей, параметры устройств и параметры приёмов.

**Обязательное —** Выбрать задачи, для которых документная модель имеет преимущество.

Для документной модели выбраны категорийно-зависимые параметры устройств и приёмов: состав их полей зависит от категории.

## Связи

**Обязательное —** Разработать минимум три коллекции, связь 1:N и связь M:N.

- **1:N:** один профиль `device_parameters` связан с несколькими приёмами через `device_profile_id`.
- **M:N:** категория PostgreSQL может иметь несколько определений, а определение — относиться к нескольким категориям; их идентификаторы хранятся в `category_ids` (например, для поля `model`).

Соответствие `device_id`, `service_order_id` и идентификаторов категорий записям PostgreSQL должно проверяться приложением; межбазовых внешних ключей нет.

## Встраивание и ссылка

**Обязательное —** Реализовать минимум один пример встраивания и один пример ссылки, обосновав выбор через характер чтения, обновления и размер документа.

В `device_parameters` объект параметров встраивается в профиль устройства:

```javascript
{
  _id: ObjectId("000000000000000000000001"),
  device_id: 2,
  category_id: 2,
  parameters: {
    model: "Samsung Galaxy A54",
    memory_gb: 128
  }
}
```

В `order_intake_parameters` параметры приёма встраиваются в документ приёма, а он ссылается на профиль устройства:

```javascript
{
  _id: ObjectId("000000000000000000000002"),
  service_order_id: 1,
  device_profile_id: ObjectId("000000000000000000000001"),
  reception_parameters: {
    screen_condition: "трещина в углу"
  }
}
```

Параметры встраиваются, потому что читаются и обновляются вместе с профилем или приёмом; документ содержит данные только одного объекта. Профиль указан ссылкой: приёмов может быть много, они изменяются отдельно и не увеличивают размер профиля.

## CRUD и проверки

**Обязательное —** Реализовать CRUD основных документов и валидацию типов, обязательных полей и 2–3 бизнес-правил.

Бизнес-правила для реализации:

1. Устройство имеет один профиль параметров, заявка — один документ параметров приёма.
2. Параметры приёма должны ссылаться на существующий профиль; профиль с приёмами удалить нельзя.
3. Параметры должны соответствовать определениям своей категории и назначения: неизвестные поля запрещены, обязательные заполнены, типы совпадают.

## JSONB и MongoDB для параметров приёма

**Желательное —** Сравнить JSONB и отдельную коллекцию MongoDB для одного сценария.

Сценарий: диспетчер сохраняет и просматривает параметры приёма вместе с заявкой.

| Критерий | PostgreSQL `jsonb` | Отдельная коллекция MongoDB |
|---|---|---|
| Хранение | Параметры находятся в строке `service_order` (`reception_parameters`). | Параметры находятся в документе `order_intake_parameters`, связанном с заявкой по `service_order_id`. |
| Связность | Заявка и параметры находятся в одной базе; применяются транзакции и ограничения PostgreSQL. | Приложение должно проверять связь с заявкой; атомарной записи между базами нет. |
| Проверка полей | Миграция задаёт `jsonb NOT NULL`, категорийные поля не проверяет. | Валидатор проверяет форму документа, приложение по определениям — типы, обязательность и допустимость параметров. |

Для текущей системы `jsonb` достаточно; выигрыш от MongoDB не подтверждён. См. `3_orders.sql`.

## Словарь коллекций и полей

**Желательное —** Составить словарь коллекций и полей.

### `device_parameters`

| Поле | Тип | Обязательность и ограничения | Значение |
|---|---|---|---|
| `_id` | `ObjectId` | Создаётся MongoDB | Идентификатор документа |
| `device_id` | `int` | Обязательно, `> 0`, уникально | Идентификатор техники в PostgreSQL |
| `category_id` | `int` | Обязательно, `> 0` | Идентификатор категории в PostgreSQL |
| `parameters` | `object` | Обязательно; поля проверяются по `parameter_definitions` | Постоянные характеристики устройства |

### `order_intake_parameters`

| Поле | Тип | Обязательность и ограничения | Значение |
|---|---|---|---|
| `_id` | `ObjectId` | Создаётся MongoDB | Идентификатор документа |
| `service_order_id` | `int` | Обязательно, `> 0`, уникально | Идентификатор заявки в PostgreSQL |
| `device_profile_id` | `ObjectId` | Обязательно; ссылка на `device_parameters._id`; индекс | Профиль устройства |
| `reception_parameters` | `object` | Обязательно; поля проверяются по `parameter_definitions` | Параметры конкретного приёма |

### `parameter_definitions`

| Поле | Тип | Обязательность и ограничения | Значение |
|---|---|---|---|
| `_id` | `ObjectId` | Создаётся MongoDB | Идентификатор документа |
| `name` | `string` | Обязательно; уникально вместе с `scope` | Имя поля параметров |
| `scope` | `string` | Обязательно; `device` или `intake` | Где используется поле |
| `type` | `string` | Обязательно; `string`, `number` или `boolean` | Тип значения |
| `required` | `bool` | Обязательно | Обязательно ли значение |
| `category_ids` | `array<int>` | Обязательно; минимум один положительный уникальный идентификатор | Категории PostgreSQL, где используется поле |

## Стратегия изменения версии документа

**Желательное —** Описать стратегию изменения версии документа.

Версия формы фиксируется в миграциях; поле `schema_version` в документах не хранится. Новое необязательное поле добавляется в `parameter_definitions`, старые документы могут его не содержать. Переименование, удаление, смена типа и добавление обязательного поля требуют миграции затронутых документов и определений до ужесточения проверки. После миграции хранится только актуальная форма документа.
