# Runbook

```bash
P="docker compose exec -T primary psql -U course_admin -d service_center"
R="docker compose exec -T replica psql -U course_admin -d service_center"
```

## Общая диагностика

Сначала нужно посмотреть, какие контейнеры запущены, затем статус primary и replica и логи. Если всё в порядке, на primary в списке реплик есть course_replica со статусом streaming и одинаковыми LSN, а на реплике is_in_recovery равно t.

```bash
docker compose ps
$P -f /course/sql/01-primary-status.sql
$R -f /course/sql/03-replica-status.sql
docker compose logs primary replica
```

## 1. Не работает replica

Видно: контейнер replica остановлен, чтение с реплики не проходит, на primary список реплик пуст. Запись на primary идёт как обычно.

Диагностика: общая диагностика, затем логи replica.

Что делать: запустить сервисы. Реплика подключится к primary и получит пропущенные изменения.

```bash
docker compose up -d --wait
```

Проверка: на primary статус streaming и одинаковые LSN, записи, сделанные пока реплика была выключена, видны на реплике.

```bash
$P -f /course/sql/01-primary-status.sql
$R -f /course/sql/04-read-probes.sql
```

## 2. Не работает primary, данные целы

Видно: запись на primary не проходит, запись на реплике тоже невозможна, потому что она только для чтения. На реплике нет подключения к primary. Чтение с реплики работает, но данные перестают обновляться.

Диагностика: общая диагностика, затем логи primary.

Что делать: запустить сервисы. Репликация восстановится без дополнительных действий.

```bash
docker compose up -d --wait
```

Проверка: репликация снова в статусе streaming, запись проходит, новая запись видна на реплике.

```bash
$P -f /course/sql/01-primary-status.sql
$P -f /course/sql/02-create-probe.sql
$R -f /course/sql/04-read-probes.sql
```

## 3. Primary потерян, восстановить его нельзя

Видно: то же, что в предыдущем случае, но контейнер не запускается или данные узла потеряны.

Диагностика: общая диагностика, логи primary, состояние тома с данными.

Что делать: сделать из реплики новый primary и переключить приложение на её порт. Автоматического переключения и прокси нет, поэтому это делается вручную. Старый primary с прежними данными рядом с повышенной репликой запускать нельзя, данные разойдутся. На стенде пересоздаем всё с нуля, при этом данные стенда удаляются.

```bash
$R -Atc "SELECT pg_promote()"
docker compose --profile restore down -v
docker compose up -d --wait
```

Проверка: узел перестал быть репликой и принимает запись.

```bash
$R -Atc "SELECT pg_is_in_recovery()"
$R -c "INSERT INTO app.replication_probe (marker) VALUES ('after-failover')"
```

По измерениям из loss.sh от аварии до первой успешной записи на новом primary проходит около 0,56 секунды. Сюда не входит время на то, чтобы заметить отказ и переподключить приложение. В трёх запусках потерь данных не было (lost=0). Репликация асинхронная, поэтому могут пропасть записи, которые не успели дойти до реплики. Верхняя граница зависит от replication lag, при массовой загрузке он доходил примерно до 14 МБ.

## 4. Данные удалены или повреждены

Реплика тут не поможет, потому что удаление базы и ошибочные изменения сразу применяются и на ней. Данные берутся из дампа. Дамп отражает состояние на момент создания, все изменения после него будут потеряны.

На стенде скрипт снимает дамп с primary, проверяет архив, запускает чистый узел restore на порту 55434 и загружает в него данные. Для локальной базы используется backup_restore.sh, он дополнительно сохраняет роли.

```bash
./experiment4.sh
./backup_restore.sh service_center_load
```

Проверка: вывод 05-integrity-check.sql на исходной и восстановленной базе должен совпадать: одинаковое число записей, диапазон id, нет дублей marker, те же ограничения.

## Ограничения

Журнал WAL не архивируется, поэтому восстановить базу на произвольный момент времени нельзя. Репликация асинхронная, автоматического переключения нет. Дамп содержит только состояние на момент его создания.
