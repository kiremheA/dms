# Решение по read/write concern и read preference

Заполните таблицу для реальных операций проекта. Не используйте одинаковые настройки автоматически для всех сценариев.

| Операция проекта | Read preference | Read concern | Write concern | Что гарантируется | Цена и ограничения |
|---|---|---|---|---|---|
| Критическая запись параметров устройства или приёма | `primary` | —: операция только пишет | `{ w: "majority", j: true, wtimeout: 5000 }` | Успешный ответ означает подтверждение записи большинством и запись в журнал primary. | Нужны primary и большинство; выше задержка. При `wtimeout` результат записи может быть неопределённым, поэтому повторять можно только идемпотентную операцию. |
| Чтение карточки сразу после сохранения | `primary` | `majority` | — | Не возвращается запись, которую большинство ещё не подтвердило; пользователь не получает отстающую реплику. | Primary принимает всю такую нагрузку; чтение может ждать majority commit. |
| Отчёт по параметрам для внутреннего анализа | `secondaryPreferred` | `majority` | — | Возвращаются данные, подтверждённые большинством, но secondary может отставать от primary. | Возможна устаревшая выдача; при недоступности secondary чтение направляется на primary. Для карточки и изменения заявки этот режим не используется. |
| Многошаговая транзакция результатов диагностики | `primary` | `snapshot` | `{ w: "majority", j: true, wtimeout: 5000 }` | Обновления профиля устройства и параметров приёма читаются из одного снимка и фиксируются атомарно после подтверждения большинством. | Транзакция работает только через primary и требует большинства; при `TransientTransactionError` повторяется вся транзакция. |

## Выбранные настройки приложения

- Connection string без секретов: `mongodb://<app-user>:<url-encoded-password>@mongo1:27017,mongo2:27017,mongo3:27017/course_app?replicaSet=rs0&authSource=course_app&retryWrites=true&w=majority`
- Retryable writes: `true` для одиночных идемпотентных записей; при неопределённом результате нельзя повторять операцию, создающую новый независимый эффект.
- Максимальное время ожидания записи: `wtimeout: 5000` мс.
- Поведение при отсутствии primary: критическая запись и транзакция не считаются успешными; драйвер обнаруживает новую топологию и повторяет только retryable write, после чего приложение сообщает об ошибке.
- Поведение при недоступности secondary: `secondaryPreferred` переключает некритичный отчёт на primary; критические операции и чтение после записи и так используют primary.
- Допустима ли устаревшая аналитическая выдача: да, только для внутреннего отчёта по параметрам; для карточки заявки и записи — нет.

## Обоснование

Параметры устройства и приёма меняют данные действующей заявки, поэтому потеря подтверждённой записи или показ старой карточки создают операционный риск: для них выбран primary и majority-подтверждение. Отчёт не влияет на решение по конкретной заявке, поэтому может читать majority-данные с secondary и принимать репликационное отставание ради разгрузки primary. Диагностика затрагивает две коллекции одновременно; `snapshot` и атомарный commit исключают частично применённый результат, но требуют доступного большинства и допускают повтор при временном конфликте.
